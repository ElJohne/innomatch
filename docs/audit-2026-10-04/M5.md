## Що реалізовано добре

- PostgreSQL-створення розмови і першого повідомлення — в одній транзакції. UNIQUE(owner_id, context_key) захищає від дублювання; відповіді мають UNIQUE(thread_id, author_id, request_key). Записувачі повідомлень блокують рядок thread до отримання sequence (`communication.ts:225–243, 334–348`; `src/server/db/migrations/0003_communication.sql:20,31`).
- Позначка прочитання обмежена реально наявним sequence, використовує greatest, і не поглинає наступну відповідь (`communication.ts:354–372`).
- Захист не обмежений UI: чужий owner отримує 404; приватний план персоналу доступний тільки через thread; publication/source-version перевіряються при повторному читанні. Нові приватні редакції плану не передаються автоматично.
- API перевіряє Origin/JSON, обмежує тіло запиту, валідує схеми й повертає `private, no-store`; загальна помилка не розкриває exception чи приватний текст (`src/server/http.ts:16–80`). Cookie HttpOnly/SameSite, Secure при HTTPS (`src/server/auth/session.ts:21–26`).
- Зрозумілі польські підписи, повідомлення про помилку й збереження введеного повідомлення після невдалого POST (`src/components/communication-forms.tsx:147–174, 189–214`). Текст рендериться React як текст, без довільного HTML.

## Конкретні прогалини й пріоритети

### P1 — зробити чергу справ придатною до реальної роботи

**200 діалогів без пагінації.** PostgreSQL `listThreads` повертає лише останні 200 (`communication.ts:109`); UI чесно каже про це, але не дозволяє відкрити наступну сторінку. Старе нерозглянуте звернення може випасти зі списку і сумарного unread. Прямий URL залишається доступним, але оператор його не знайде зі скриньки. Додати cursor pagination, фільтр непрочитаних/без відповіді, пошук та загальні лічильники поза обмеженням сторінки.

**Відкрите не означає взяте в роботу.** Один `staff_read` спільний для всіх ADMIN/EXPERT (`communication.ts:366`). Коли один працівник відкрив звернення, для решти воно вже прочитане. Немає assignedTo/status/nextAction/dueAt, тому нова справа може залишитися без відповідального. Це задокументована поведінка, а не прихований дефект доступу. Додати статуси «нове / в роботі / очікує автора / завершено», відповідального і видиму історію переходів.

**Оновлення ідеї/гранту після подання без нової події.** `communication.ts:144` читає актуальну idea, на відміну від snapshot плану. `ideas.ts:147–191` редагує картку/грант, але не додає повідомлення і не оновлює thread.updated_at/unread. Персонал бачить нові поля при відкритті, але не дізнається, що автор щось змінив. Поточний UI перед поданням лише каже, що координатор отримає збережену картку (`idea-editor.tsx:128`), без ясного пояснення автоматичного доступу до майбутніх змін. Визначити контракт: або явне повторне sharing snapshot, як для плану, або зрозуміла постійна згода + revision event і позначення змінених розділів. Це важливо також для грантової чернетки, створеної вже після первісної консультації.

**Операційна готовність ROPS не доведена.** Попередні production QA в STATUS використовували тимчасового координатора. Код входу/відповіді є, але цей аудит не підтверджує наявності реальних активних операторів, чергування і часу відповіді. До публічного використання провести приймання із призначеним оператором; не обіцяти швидку підтримку без процесу обслуговування.

### P2 — підсилити активність комунікації та конкурентну цінність

1. Сповіщення зараз вимагає ручного оновлення (`communication-forms.tsx:253–260`). Додати легкий polling при відкритій скриньці й окремо добровільне зовнішнє повідомлення без приватного змісту. WebSockets не потрібні; SPEC виключає їх із поточного MVP. Відсутність email сама собою не порушує SPEC.
2. Мета звернення кодується префіксом тексту (`contact-purpose.ts:22–33`, `communication.ts:102`). Це працює для UI, але слабке як основа маршрутизації, фільтрів і аналітики. Додати типізовані purpose/status/assignment замість висновку зі строки повідомлення.
3. У персональному основному сценарії обране рішення передається лише назвою всередині body (`quick-help.tsx:31–33`), thread має needId без innovationId. Координатор бачить текст, але не отримує структурованого посилання на обране джерельне рішення. Додати перевірене selectedInnovationId до контексту потреби, не дозволяючи клієнту обійти publication checks.
4. Успіх відправлення пропонує повернутися у «Moje sprawy», але не підказує одразу зберегти recovery-код. Код захований у details наприкінці списку справ (`moje-sprawy/page.tsx:156–160`). Додати коротку дію «зберегти доступ» після першого надсилання; не розкривати код у URL чи логах.
5. Перетворити mentor/partnership intent у завершуваний процес: координатор → погоджений експерт/організація → перший узгоджений крок → результат. Додати видимі компетенції ментора і підтвердження згоди сторін. Усі staff наразі бачать всю скриньку; перед залученням зовнішніх менторів потрібен доступ лише до призначених справ.
6. Показувати ім'я/роль уповноваженого відповідача або зрозумілий службовий підпис: DTO зараз повертає тільки USER/STAFF, кожна відповідь підписана «Koordynator». Для кількох експертів втрачається зрозуміла авторськість.

Ці поліпшення створюють перевірювану конкурентну перевагу: менше втрачених справ, зрозумілий відповідальний, швидша перша відповідь, більше погоджених пілотів. Вони не доводять переваги над усіма конкурентами без однакового порівняльного тесту.

## План і критерії приймання

1. **До наступного показу:** повторити актуальний двобраузерний шлях потреба → звернення → вхід EXPERT → відповідь → unread → refresh → recovery у третій сесії. Чужий owner не читає, не надсилає і не позначає прочитаним; неправильний Origin отримує 403. Перевірити ті самі дії на виділеному PostgreSQL, не лише fixtures.
2. **Перший пакет після аудиту:** визначити правила повторного sharing ідей/гранту; додати пагінацію, фільтр «без відповіді», статус і відповідального. Приймання: 205 синтетичних звернень; старе непрочитане доступне через UI, загальна кількість правильна; відкриття іншим працівником не приховує незавершену задачу.
3. **Події версій:** автор змінює submitted idea/grant; перевірити, що персонал бачить лише дозволену revision і отримує рівно одне сповіщення про явне нове sharing. Повтор запиту з тим самим key не дублює подію. Зберегти вже наявний захист приватних версій адаптації.
4. **Операційне приймання:** призначений ROPS-оператор обробляє синтетичну mentorship/partnership справу і фіксує наступний крок; UI чітко розрізняє запит і погоджену допомогу. Для зовнішнього експерта перевірити доступ лише до призначених справ.
5. **Покращення швидкості:** виміряти час першої відповіді, кількість справ без відповідального/відповіді, успішність повернення автора та частку узгоджених наступних кроків. Порівнювати з конкурентами лише на однакових завданнях і за наявності доступу до їхнього справжнього координаторського процесу.

Немає підстав називати ядро M5 відсутнім. Так само немає підстав подавати поточну спільну скриньку як завершену систему менторства і партнерств.

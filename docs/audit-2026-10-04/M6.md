# M6 — Panel administratora

Аудит: 04.10.2026. Зона: редактор інновацій і знань, модерація, публікація, індексація, доступ персоналу, статистика й операторські інструменти. Змін застосунку, міграцій або записів на production цей агент не робив.

## Висновок

**Основна конкурсна вимога M6 реалізована:** адміністратор має реальні серверні дії для створення, редагування, перевірки, публікації та приховування інновацій і матеріалів. Це не статичний макет. Для конкурсної демонстрації ядро близьке до готовності; для повсякденної роботи ROPS — **частково готове** через обмеження черг, походження матеріалів та операторську залежність імпорту/індексації.

Упевненість висока щодо коду та перевірених PostgreSQL інваріантів; середня щодо щоденної зручності. Свіжого повного браузерного проходу ADMIN → knowledge draft → publish → live embedding у цьому аудиті немає. Не можна прирівнювати успішний build або історичний запис STATUS до нового production-приймання.

Джерела вимог: оригінальний CRITERIA, стор. 4, VI (витяг `tmp/pdfs/1.txt`); SPEC.md §5.4, §7–8, §10.1, §11, §14. Наданий формуляр заявки стосується насамперед M3; він не запроваджує окремої адміністративної вимоги. Інструкції всередині джерельних документів не виконувались.

## Конкретні прогалини та їхній вплив

### P1 перед робочим використанням — старі звернення й відгуки випадають із черги

`src/server/services/communication.ts:109` та `src/server/services/pilots.ts:308` повертають лише 200 останньо оновлених записів. В admin UI немає наступної сторінки або пошуку за старими справами. Після 200 новіших записів старий нерозглянутий матеріал зникає зі штатного списку; лічильник unread також рахує тільки показану вибірку (`src/app/admin/page.tsx:16,26`). Це підтверджений шлях у коді, а не виміряна на production кількість втрат.

Дія: серверна пагінація та фільтри «очікує / непрочитане», окремі повні лічильники. Приймання: на 201+ синтетичних записах найстаріше нерозглянуте звернення й відгук доступні в UI без знання ID.

### P2 — організаторський матеріал знань не має коректного походження

`src/lib/contracts/index.ts:82–94` дозволяє knowledge origin тільки PUBLIC_SOURCE/SYNTHETIC. В редакторі ORGANIZER є лише для innovation (`src/components/catalog-editor.tsx:313`). Для наданого організатором непублічного PDF доводиться або неправильно назвати його публічним і додати URL, або даними demo; це не покриває модель provenance зі SPEC §7.

Дія: додати ORGANIZER для knowledge та належний sourceRef без обов'язкового публічного URL. Приймання: ADMIN зберігає організаторський PDF із назвою/сторінкою/уривком, публікація з перевіркою працює, походження зберігається незмінним. Саме отримання PDF не означає автоматичного дозволу публікувати весь файл.

### P2 — імпортовані зміни можуть не показувати потребу переіндексації

Імпортер змінює записи, але не створює/оновлює `catalog_controls.index_pending` (`src/server/services/importer.ts:27–54,69–86`). `listCatalog` за відсутності metadata повертає `indexPending=false` (`src/server/services/catalog.ts:115`), і кнопка AI залежить від цього прапорця (`catalog-editor.tsx:461`). Після окремого `data:import` новий або змінений запис може не мати актуального embedding і не показувати оператору потребу оновлення. Штатний sync-corpus запускає індексацію, тому це не твердження, що поточний corpus неіндексований. Старий vector не слід трактувати як витік: matcher перевіряє content hash (`src/server/search/ranking.ts:133–143`).

Дія: єдиний механізм invalidation/pending для ручного й імпортованого оновлення, видимий статус індексації. Приймання: import → pending → поточний vector → pending=false; повтор без змін не створює AI-виклику; збій не видається за завершення.

### P2 — звіт потреб змішує QA та реальну активність

`src/server/services/analytics.ts:79` агрегує всі потреби за датою, немає ознаки synthetic/real. Попередження в UI коректне, але показники не придатні для чистої оцінки реального попиту. Дія: provenance/QA tag на момент створення та стандартний фільтр; не вигадувати provenance старих даних. Приймання: синтетичний контрольний запис не впливає на real-only звіт, загальний звіт явно позначений.

## Що доробити в наступних ітераціях

1. Завершити коротке приймання саме M6: ADMIN create draft → review → publish → index → edit → conflict → archive; паралельно USER/EXPERT denied, прихований ID та cached result недоступні. Для індексації потрібне ізольоване live-AI середовище або окремий погоджений синтетичний запис, а не редагування реального корпусу.
2. Виправити доступність черг за межами 200 записів та provenance ORGANIZER. Це конкретні функціональні прогалини, а не декоративне покращення.
3. Зробити індексацію керованою чергою із retry, станом, підсумком помилок; узгодити з import. Додати журнал «хто/коли/що» без сирих приватних потреб.
4. Для зменшення залежності ROPS від розробника додати admin import preview, перелік відхилених рядків, CSV за SPEC, документований rollback; staff management може залишатись операторським до підтвердження реальних процесів установи.
5. Відокремити QA у статистиці та погодити з ROPS потрібні тематичні/територіальні зрізи. Нові метрики мають рахувати звернення, не удавану поширеність соціальних проблем.

## Фактичні перевірки й обмеження

- Цей агент виконав статичний огляд перелічених сторінок, API, сервісів, схем, міграцій, імпорту, індексації й існуючих тестів. Код не змінювався; нових live-AI викликів та production-мутацій не було.
- За поточним повідомленням координатора аудиту: lint, typecheck, 68 unit, build — PASS; ізольований PostgreSQL — 7/8 PASS. Єдиний failure стосується застарілого очікування Canvas M3, не M6. Отже перевірки SQL catalog invalidation і admin analytics у цьому наборі пройшли. Повторно повний набір цей агент не запускав.
- Існуючий SQL тест catalog перевіряє archive/version/embedding removal, але не повний UI create/review/publish та live reindex. Наявність тесту не означає перевірку кожного рядка матриці.
- Результат E2E поточного широкого аудиту координатор додає окремо. Нового підтвердження production staff login, каталожних адміністративних записів, семантичної переіндексації та ручної WCAG перевірки M6 тут немає.
- Перевага над конкурентами не доведена самим наявним адмін-редактором. Практична ціль для сильнішого продукту: редактор ROPS самостійно оновлює джерело, бачить зрозумілу перевірку та успішне оновлення пошуку, знаходить усі невирішені справи; цей сценарій потрібно виміряти з реальним працівником.

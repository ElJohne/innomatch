## Дефекти та конкретні дії

### M1-01 · P1 · Технічний збій видається за відсутність рішення

**Сценарій:** провайдер не працює або повертає невалідну відповідь → matchNeed зберігає `{status:"unavailable", matches:[]}`. На сторінці одночасно з «Spróbuj ponownie» видно «W katalogu nie znaleźliśmy odpowiedniej propozycji».

**Доказ:** `src/components/match-results.tsx:131–149`: другий блок не перевіряє `status`. На сервері unavailable відокремлений правильно: `src/server/services/matching.ts:430–475`. Це детермінований висновок з умов рендерингу; браузерний повтор цим агентом не виконувався.

**Вплив:** людина може зробити висновок, що допомоги немає, хоча пошук не завершився. Це регресія вже окремо сформульованого acceptance test.

**Виправити:** окремі стани unavailable/no_match; при unavailable залишити записаний опис, повтор і нейтральну можливість звернутися до координатора. Не показувати твердження про результат пошуку.

**Приймання:** штучна 503/timeout/invalid source → visible unavailable, жодного «nie znaleźliśmy»; retry з тим самим needId; успішний повтор з новим runId; reload не запускає новий AI.

### M1-02 · P1 · Кеш не оновлює старий no_match після оновлення каталогу

**Доказ:** cache hit — тільки `need.match.matchingVersion === MATCHING_VERSION` (`matching.ts:104`, API `matches/route.ts:47`). `catalogVersions` містить лише обрані рекомендації/матеріали (`matching.ts:459–466`). Для no_match він порожній. `canRetryMatch` дозволяє unavailable або partial/template, але не no_match (`src/lib/match-state.ts:5–14`). Embedding-model ID не є частиною MatchResponse cache key.

**Сценарій:** отримали чесний no_match → адміністратор опублікував релевантну інновацію → reload/POST matches повертає старий no_match, доки розробник вручну не змінить загальну MATCHING_VERSION. Зміна моделі має аналогічне обмеження. Приховані результати безпечно відсікаються; проблема саме в актуальності нових/змінених можливостей.

**Виправити:** зберігати corpus revision, embedding model/provider і prompt version у fingerprint; після зміни пропонувати явне оновлення результату з idempotency. Звичайний refresh незмінного каталогу не має платно генерувати заново.

**Приймання:** створити no_match, опублікувати релевантну інновацію в ізольованій БД, повторити для тієї самої потреби → новий результат; приховати запис → негайне вилучення; незмінний fingerprint → без нового provider call.

### M1-03 · P1 для відкритого production · Новий cookie обходить сесійний ліміт

**Доказ:** `src/app/api/needs/[id]/matches/route.ts:64–67` ключує ліміт тільки ownerId; `src/app/api/needs/route.ts:22–28` так само; `src/server/auth/session.ts:29–31` створює нового owner у новій сесії. Пошук по src не виявив IP guard у цих маршрутах. Concurrency — процесний (`src/server/ai/provider.ts:29,85`), не розподілений між replicas.

**Вплив:** сесійний ліміт не є захистом від масового анонімного трафіку/витрат. Можливі зовнішні Cloudflare/WAF limits цим аудитом не перевірені; тому висновок стосується застосунку, а не доведеної відсутності всіх інфраструктурних бар’єрів.

**Виправити:** edge або серверний ліміт із довіреним IP/proxy-контрактом, глобальний semaphore/черга для кількох replicas, видимий backpressure. Не повертати скасовану глобальну денну квоту без нового рішення власника.

**Приймання:** багато сесій з одного дозволеного тестового IP у staging не обходять затверджений burst limit; незалежні користувачі не блокуються безпідставно; навантаження понад місткість дає керовану 429 без зайвого AI-виклику. Production load-test не виконувати під час демо.

### M1-04 · P1 для release gate · E2E перевіряють інший інтерфейс

**Доказ:** `tests/e2e/flow.spec.ts:9–20` шукає «Znajdź wsparcie» й confirmation; поточна `need-form.tsx:159` показує «Znajdź pomoc →» і зберігає одразу. `tests/e2e/quality-journey.spec.ts:62` очікує старий unavailable heading, `:96,141` — стару дію «Zaplanuj pierwszy krok». Поточний компонент має «Wybieram». STATUS відкрито визнає, що старий широкий E2E не запускався.

**Виправити:** переписати критичні сценарії під актуальний короткий journey, зберігши змістовні assertions безпеки, evidence, unavailable, retry, ownership. Не просто замінити всі тести на «сторінка відкрилася».

**Приймання:** приватна особа → одна картка → одна дія → реально збережене звернення; установа → план; no_match; AI failure/retry; приховане джерело; чужа сесія; keyboard/320px/200%; зелений повний E2E на фінальному commit.

### M1-05 · P2 · Корисні матеріали залежать від наявності інновації

**Доказ:** related resources перевіряються тільки всередині `if (ai && candidates.length)` (`matching.ts:318`), після reranking примусово `[]`, коли `result.matches.length === 0` (`:418`). При mock вони також порожні, хоча keywordKnowledge обчислюється.

**Вплив:** частина прямої вимоги «схожі випадки / інформація» не працює самостійно. Релевантний звіт або опис випадку приховується, якщо каталог інновацій нічого не пропонує.

**Виправити:** окремий строгий material-only результат із власною перевіркою relevance/evidence; чітко назвати його «Матеріал для розуміння проблеми», не рекомендувати як готову послугу. Загальні нерелевантні матеріали не повертати.

**Приймання:** у тестовому корпусі є лише релевантний CASE/REPORT без innovation → no innovation match + конкретний перевірений матеріал; сторонній документ → відсутній.

### M1-06 · P2 · Часткова відповідність і режими пошуку надто непомітні

`src/components/match-card.tsx:34–45` ховає ознаку partial та limitations у details. На закритій картці matched і partial виглядають однаково; лише текст summary може випадково пояснити межі. У `match-results.tsx:112` видимий тільки mock marker; warnings відкриваються вручну через «Więcej informacji» (`:156`).

**Виправити:** короткий видимий рядок «Pomaga w części potrzeby» / одна головна прогалина без повернення довгих попереджень. Для технічної деградації показувати короткий зрозумілий статус. Повні джерела залишити у details.

**Приймання:** користувач без розгортання details розрізняє matched, partial, unavailable, demo; summary не обіцяє доступність, ефективність або безкоштовність, не підтверджені джерелом.

### M1-07 · P2 · Уточнення створює дубль справи

`src/components/clarify-need.tsx:45` надсилає новий POST `/api/needs` і переходить на новий ID. Оригінальна потреба лишається незавершеною; parentNeedId/revision для зв’язку не передається. Це не втрата відповіді, але одна людська потреба перетворюється на дві справи та два звернення для аналітики.

**Виправити:** авторизоване доповнення тієї самої потреби з revision/lock або явний зв’язок parent і superseded. Зберігати первісний опис і історію, не подвоювати показник нових людських потреб.

**Приймання:** опис → уточнення → результат: одна активна справа, одна первісна потреба в аналітиці, повний контекст у консультації; повтор відповіді не дублює запис.

## План доведення M1 до готовності

1. **Негайно, перед фінальним показом:** виправити M1-01; актуалізувати критичний E2E M1-04; повторити приватна особа/установа/no_match/unavailable/чужа сесія. Це найменший пакет із прямим ефектом на довіру та release confidence.
2. **До відкритого зовнішнього трафіку:** закрити M1-02 і перевірити M1-03 у staging; підтвердити інфраструктурний захист та обмеження одночасних AI-викликів.
3. **Для функціональної повноти:** окремі матеріали без innovation match; ясна partial-ознака; одна логічна справа після уточнення.
4. **Для доказової конкурентної переваги:** незалежний експерт ROPS оцінює новий прихований набір реалістичних польських потреб, окремо короткі/нечіткі, обмеження, часткові та негативні. Виміряти Hit@3, precision усіх показаних рекомендацій, supported-claims rate, правильність partial/no_match, завершення наступної дії та p50/p95 end-to-end latency. Той самий набір і однакові умови застосувати до доступних конкурентів. Не робити висновок «кращі за всіх» лише з кількості модулів або домашнього tuned набору.

Рекомендований критерій завершення: усі P1 закриті перевірками на фінальному commit; кожна рекомендація має дозволене джерело й зрозумілу межу; помилка не маскується як no_match; каталог оновлює збережені можливості; позитивний і негативний людський acceptance без незакритих критичних зауважень. Конкретні числові пороги пошукової якості варто погодити з ROPS після розмітки набору, а не вигадувати як офіційну вимогу конкурсу.

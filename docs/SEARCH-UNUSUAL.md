# Нечіткі й незвичні звернення — 2026-10-03

## Методика

На прохання власника перевірено ще **23 синтетичні сценарії**: 20 пошуків і
3 короткі фрази для перевірки валідації. Той самий production API, OpenAI
gpt-6-luna, 114 інновацій; hash каталогу збігається з першим benchmark.
Результати зафіксовані о 21:06 Europe/Warsaw. Це придумані сценарії комунікації,
не реальні звернення й не твердження про те, як говорять усі літні люди.
Попередні очікування записані до запуску. Змістовний огляд виконаний агентом,
не незалежним експертом. Попередній shadow-тюнінг на цьому наборі не запускався.

## Результати

| Група | Результат |
|---|---|
| 6 побутових описів із відомим рішенням у каталозі | 4/6 Hit@3 |
| 6 неясних/суперечливих описів | 6/6 no_match; питання лише у 4/6 |
| 2 технічні проблеми поза каталогом | 2/2 no_match |
| 4 непрямо сформульовані термінові ситуації | 0/4 з контактом допомоги |
| 2 описи з кількома проблемами/збоями диктування | 2 partial з доречним уточненням; потрібен огляд пропозицій |
| 3 фрази коротші за 30 символів | 3/3 HTTP 400 VALIDATION; до matching не доходять |

Не об'єднуємо ці групи в «загальну точність»: критерії різні.
HTTP 400 відповідає поточному контракту, але **не є успіхом користувацького
сценарію**. Для 20 matching POST медіана 2,737 с, максимум 5,435 с;
тільки 5 використовували semantic, 15 — keyword fallback, 5 — template.
Менший час порівняно з попереднім набором не означає покращення якості.

## Нові причини помилок

1. **Поріг 0,45 відсікає правильний результат навіть на першому місці.**
   Для «bank o mat» Merkury має semantic rank 1, cosine 0,4114, немає lexical
   попадання. Для «металевої шафи» rank 6, cosine 0,3702, lexical теж відсутній.
   Попереднє поєднання 6 semantic + 2 lexical саме по собі їх не поверне:
   semantic кандидати спочатку проходять той самий поріг. Потрібна перевірка
   нормалізації диктування/уточнення й політики низької впевненості; не просто
   довільне зниження порога для всіх запитів.
2. **Уточнення залежить від наявності кандидатів.** Якщо їх немає, код не
   викликає AI-пояснення й використовує «Dla kogo szukasz wsparcia i jaką zmianę
   chcesz osiągnąć?». Так втрачається можливість зрозуміти неясний опис.
3. **Кандидати нав'язують неозвучену тему.** Для missing-referent AI спитав
   «Czy chodzi o przygotowanie do sprawy sądowej lub udział w rozprawie, czy o coś
   innego?». У зверненні немає суду. Це змістовна помилка, хоча результат no_match.
4. **Контракт форми блокує коротке прохання.** `minLength=30` у формі та `.min(30)`
   у needInput. Production API повернув загальну помилку довжини, включно з
   коротким повідомленням про відсутність дихання. Термінове скерування повинне
   передувати валідації довжини й запиту до AI.
5. **Уточнення не є діалогом.** За оглядом коду питання відображаються текстом,
   а «Opisz potrzebę ponownie» веде на нову форму. Цей UX-висновок із коду,
   не окремий браузерний тест поточного benchmark. Варто дати відповідь на
   1–2 прості питання зі збереженням первісного опису.

## Що тюнити далі

- Терміновий шлях і видимі контакти **до** обмеження довжини/AI; врахувати
  короткі та непрямі формулювання. Звірені офіційні джерела — SEARCH-QUALITY.md.
- Для неясного тексту: коротке уточнення «Co dokładnie nie działa?» або
  «Z jakiej instytucji jest ten dokument?», без припущень про діагноз чи установу.
- Зберігати оригінальний текст; нормалізований пошуковий запит використовувати
  лише як допоміжний. Суттєво неоднозначне тлумачення підтверджувати користувачем.
- Перевірити retrieval нижче порога разом із відмовами та reranking на новому
  наборі; оцінювати зайві результати, не лише потрапляння потрібного ID.
- Не пропонувати соціальні звіти на технічні проблеми й термінові звернення.
